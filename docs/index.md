# CUDA Hammer: A Tensor Compiler in C++

*From a Minimal IR to Fused, Autotuned Kernels*

Every tensor framework a reader has used -- PyTorch eager mode, a hand-written CUDA kernel, a NumPy script -- runs one operation at a time: allocate an output, launch a kernel, wait, move to the next line. That works, but it leaves real performance on the table in a specific, nameable way: every intermediate result round-trips through memory even when nothing outside the current computation ever needed it there, and every kernel launch pays its own fixed overhead regardless of how little work it does. A compiler that sees the *whole* computation graph before generating any code can fix both: fuse a chain of operations into one kernel so an intermediate value never leaves a register, and pick the loop tiling, ordering, and unrolling that the specific hardware it is targeting actually rewards. This book builds that compiler, called CUDA Hammer, from nothing -- no LLVM, no MLIR, no borrowed IR -- one real, working piece at a time.

This book is independent: it does not assume or reference any other book in any series, and it builds every piece of CUDA Hammer from Chapter 1 rather than pointing elsewhere for it. What it keeps is the same discipline its sibling books follow: every piece of code in this book is genuinely compiled, and wherever a real answer does not require hardware this book's own authoring environment does not have, it is genuinely run and checked against an independent reference. Where a claim depends on hardware this environment does not have -- a real GPU to execute CUDA Hammer's own generated CUDA kernels on -- that limitation is stated plainly rather than papered over with a fabricated number; Getting Started explains exactly where that line falls for this book.

## What this book covers

- **Part 0 -- Why Compile Tensor Programs At All.** The real, measurable cost of eager execution, what a general compiler pipeline actually looks like end to end, and a tour of how three real production ML compilers -- XLA, TVM, and Triton -- are actually built.
- **Part 1 -- CUDA Hammer's IR: A Minimal Tensor Graph From Scratch.** Representing tensors and operations as a graph, a small frontend for building that graph, shape inference and validation, and tooling to print and visualize CUDA Hammer's own IR while developing it.
- **Part 2 -- Basic Optimization Passes.** A real pass manager for structuring transformations, constant folding and dead code elimination, common subexpression elimination over a tensor graph, and algebraic simplification.
- **Part 3 -- Operator Fusion.** Why fusion matters in the first place -- the real arithmetic-intensity argument behind memory-bound versus compute-bound kernels -- elementwise fusion, fusing reductions, loop fusion and tiling for the fused result, and precisely which fusion boundaries a real compiler cannot cross, and why.
- **Part 4 -- Code Generation.** Lowering CUDA Hammer's high-level IR to an explicit loop nest, generating real CUDA C++ from the fused IR, generating real vectorized CPU code, and a JIT backend that compiles and loads generated code at runtime.
- **Part 5 -- Autotuning.** The real search space a kernel's own schedule lives in (tile sizes, loop orders, unrolling), cost models versus genuine on-hardware measurement, building CUDA Hammer's own autotuner, and caching tuned schedules for reuse.
- **Part 6 -- Case Studies.** How CUDA Hammer's own design choices compare to XLA's HLO fusion passes, TVM's Relay/TIR and Ansor auto-scheduling, Triton's block-level programming model, torch.compile and TorchInductor, Flash Attention read as a fusion case study, and quantization-aware code generation.

## How to read this book

Every chapter follows the same shape: an intuition built from a concrete picture before any code, a background section with the real, complete implementation, one or more worked examples with genuinely computed output, a `[COMMON TRAP]` callout naming a specific, real mistake rather than a vague warning, a chapter summary, self-check questions, and worked solutions. Code that can genuinely run in this book's own authoring environment is genuinely run and its exact output locked into the page. Code whose correctness depends on hardware this environment does not have -- CUDA Hammer's own generated CUDA kernels, specifically -- is genuinely compiled for a real architecture and checked instead by a host-side reference implementation of the same computation; Getting Started explains this discipline in full.
